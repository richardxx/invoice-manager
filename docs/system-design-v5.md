# InvoiceManage 1.5.12 system design

## Scope and storage

The Java Swing application runs from `D:/program/InvoiceManage` with JDK 25. The selected work directory contains `invoice-manager.db`, original PDF files, avatars, staging files, and settings. The default work directory is `%LOCALAPPDATA%/LocalInvoiceManager`; changing it copies and verifies the existing data before switching. Application upgrades never remove that directory.

Startup creates a light retro splash window before opening the work directory. A background worker acquires the existing single-instance lock, resolves or migrates the work directory, and initializes the database while publishing phase progress on the Swing event thread. The main window is revealed only after it has been constructed and the progress bar reaches 100%. Initialization failures close the splash and report the error. The Help menu opens a five-step illustrated guide and a six-scene About comic. About opens on its first, static picture with no playback hint; three clicks on the picture start a hidden playback sequence that changes panels every three seconds and stops on the final panel. Its fixed width follows the illustration's aspect ratio. Captions and credits are rendered as Swing text so Chinese remains legible. All artwork is bundled under `src/main/resources/art/` and does not read or alter invoice data.

SQLite is the source of truth for people, invoice metadata, assignment, intake status, and reimbursement state. Original PDFs are stored separately under `originals/` and addressed by a managed relative path. Metadata updates never rewrite a PDF.

## Data model and migration

Schema version 2 extends the version 1 `invoice` table with `intake_status` (`IN_POOL` or `DELETED`) and nullable `reimbursed_at`. `reimbursement_month` records each month, its nullable `completed_at`, and `updated_at`. Schema version 3 adds six nullable payment fields to `person`; older people retain their records and must fill payment details before bank export. Before upgrading a version 1 or version 2 database, startup saves a versioned backup in the work directory. Migrations add columns without replacing existing rows and check for already-added columns so an interrupted migration can resume. Tests verify both upgrade paths.

Pool deletion is a soft delete: the invoice is hidden, its owner and reimbursement month are cleared, and the original file remains in the work directory and backups. Re-importing identical PDF bytes restores the record. A paid invoice cannot be deleted, edited, unassigned, or reassigned until the month is reopened.

Completing a month is one SQLite transaction: all currently assigned invoices in that month receive `reimbursed_at`, and the monthly completion row is updated. Undo clears those values in one transaction. Empty months cannot be completed. Assignments into a completed month are rejected. The reimbursement matrix sums known positive amounts for all assigned invoices by category, including those awaiting review. The pending count remains visible. Both exports include only review-ready invoices. The people list's completed total sums positive amounts from paid invoices across months. The pool and month summary show paid state independently of review status.

## Recognition

New imports call `RecognitionService` only: extract embedded PDF text first, return it when the key fields are complete, and otherwise render pages for local OCR while keeping reliable text-layer fields. Import never calls an AI endpoint, including when an older settings file contains `ai.enabled=true`. The right-click AI action is the sole model entry point. It requests the configured endpoint, reports preparation, request, and response phases in the pool status bar, and merges successfully parsed fields into the existing invoice. When no model is configured it opens Options. An error leaves the original metadata unchanged; the status bar shows a short yellow warning that opens the full exception details.

The right-click OCR action runs local recognition on the saved original, including forced OCR of its rendered pages even when embedded text exists. Embedded text normally takes precedence when it yields a field; OCR fills gaps. Re-recognition preserves assignment and reimbursement month, marks the record for human review, and does not run on a paid invoice. The parser accepts spaced buyer/seller labels and multiline tax-inclusive totals. For rasterized airline itineraries, itinerary terms trigger a second OCR pass using a table-oriented page mode. The parser reads the final CNY total from the fare table rather than the base fare or tax components, recognizes `填开单位` and `填开日期`, and finds the 20-digit invoice number. Scanned results remain pending review; a passenger name that OCR cannot read is left empty. Existing records are reprocessed only when the user chooses a recognition action.

For landscape standard e-invoices, full-page OCR can place the buyer and seller `名称` fields on one line and lose the vertical seller label. When paired name and tax-ID signals identify that layout, recognition also reads a normalized upper-right seller area if the seller is missing or suspect, or the user explicitly requests OCR. The parser accepts a company name only from that area and rejects tax-ID/header text. A reliable PDF text-layer seller still wins on normal import; explicit OCR may use the region result. The cropped result remains subject to human review. The supplied annotated screenshot is wrapped as a scanned PDF in an optional integration test, without storing its personal contents in the repository.

## UI workflow

Dropdown arrows, month navigation, pool assignment markers, ZIP import checks, AI/OCR progress, success, and warning markers are painted as Java2D icons. Labels contain plain status text, so a missing emoji font cannot turn these controls into square glyphs. The progress timer updates the drawn spinner without changing the phase text.

The pool table separates review state from reimbursement state. Right-click actions include assignment, unassignment, editing, AI recognition, OCR recognition, original PDF opening, and deletion. `计算金额` is enabled for a multi-row selection and sums its known invoice amounts with checked arithmetic; the result dialog identifies any selected invoices with missing amounts. Deleting an assigned invoice warns that its named owner will be unassigned. Deletion of a paid invoice is disabled in the menu and rejected by the service.

The monthly reimbursement view lists only people assigned in the selected month. Entering `YYYY-MM` and pressing Enter changes month. A single click selects a cell. Double-clicking a person's name, assigned count, or row total opens all their invoices for that month; double-clicking a category amount filters to that category, and double-clicking the pending count filters to invoices needing review. The action button reads `完成报销` for open months and `撤销报销` for completed months; either action requires a confirmation dialog. The detail view shows each invoice's paid state.

The invoice export first asks for a parent directory, then opens a modal filename preview. `ExportService.previewMonth` takes a snapshot of review-ready invoices and generates the default pinyin-category-amount PDF names, including collision suffixes. Confirmation validates unique Windows-safe `.pdf` names; cancellation writes nothing. At export time, the service checks the invoice IDs, owners, amounts, and categories against the preview, copies originals into a temporary sibling directory, then moves it to a new `yyyymm` folder after all copies succeed. An existing month folder is rejected, so prior exports cannot be overwritten.

`BankExcelExportService` groups review-ready invoices for the selected month by person and excludes the fixed company account. It checks that each personal payee has all six required fields, then loads the bundled original `.xls` template and fills only `其他代发批量文件-混合`. Each personal payee receives one data row. A month containing only company reimbursements has no bank file to export. Company invoices remain in reimbursement views and totals. Account, CNAPS, and document numbers use text cells so leading zeros survive; the amount is a numeric cell formatted to two decimals. The other template sheet is preserved. The UI asks for an `.xls` destination and confirms replacement of an existing file.

The people table opens the editor on a double-click in its name column. The modal editor has an explicit 820×640 size and a scrollable form; Save keeps the dialog open if validation fails. Document type is restricted to the four listed dropdown choices, with `居民身份证` selected for new records. Legacy `身份证` values are normalized to `居民身份证`; unsupported legacy values remain unselected until the user chooses a supported type.

## ZIP intake

The pool accepts ZIP files through drag and drop and the file chooser. `ZipInvoiceImportService` traverses ZIP entries in folders and nested ZIPs (up to three nested levels). Archive paths are displayed only; extracted PDFs receive generated temporary names under the work directory's `staging/` folder, so `../` names cannot write outside it. Screening uses local PDF text and OCR. A candidate with a positive amount plus an invoice number, or seller and issue date, or railway traveler and travel date is auto-imported. Other PDFs remain selectable in the results dialog. Screening results do not depend on an external AI endpoint.

The modal results dialog lists every encountered PDF, its detected fields, outcome, and message. Imported items show a drawn check icon; duplicates are identified. A double-click opens the saved original or temporary PDF. Multi-selection and `导入所选` call the normal local direct-PDF importer for missed items; this action does not call AI. The dialog keeps temporary PDFs available while the user reviews them and removes its own staging directory when closed. ZIP entry counts, depth, PDF size, archive size, and total extracted bytes are bounded. A damaged archive is reported as a warning while results already processed remain visible.

## Verification

Run `mvn test` and `mvn package` with JDK 25. Tests cover version 1 and version 2 migrations, persisted completion and undo, paid invoice restrictions, soft deletion and restoration, monthly UI state, zero model requests on import with credentials configured, manual AI request phases through a local mock server, OCR parsing, and the supplied restaurant invoice PDF. Invoice export tests verify default and edited filenames, PDF copies in the `yyyymm` folder, duplicate and unsafe filename rejection, and stale-preview rejection. Bank export tests reopen the saved `.xls`, verify the template header and sheets, per-person totals, text identifiers with leading zeros, and missing-payment rejection. Optional integration tests check the supplied scanned airline itinerary, ZIP auto-detection, and seller extraction from the supplied standard-invoice screenshot. ZIP intake tests cover nested folders and archives, duplicate PDFs, path traversal names, missed-file override, damaged archives, GBK filenames, and auto-detection of the supplied restaurant invoice. No production AI endpoint is called by tests. Use `Run-InvoiceManage.ps1` to launch the built JAR through a hash-addressed copy, avoiding a partial JAR load during later builds.

The package lifecycle runs Maven Shade first, then a scoped Ant cleanup step. Cleanup checks that the current runnable JAR exists and removes only matching `invoice-manager-*.jar` and `original-invoice-manager-*.jar` files directly under `target/`, excluding the current runnable JAR. It also attempts to remove `invoice-manager-*.jar` launch snapshots under `work/run-cache/`; locked copies are left for a later build. It runs after successful packaging and does not touch work-directory data, backups, or other target files.
